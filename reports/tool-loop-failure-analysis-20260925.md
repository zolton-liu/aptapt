# 工具调用循环错误总结与改造

日期：2026-09-25
分支：`dev/local-verifier`

## 结论

当前低 pass@1 不是一个原因造成的。固定十题完整基线 v6.6 为 2/10；v6.7 加入五类经过公开 checker 工程验证的高层算子后，中断前六题为 5/6，但该结果不是完整十题 pass@1，不能作为达标成绩。轨迹显示，高层算子方向有效，但模型在真正调用算子前仍浪费大量请求，工具循环还会把“动作不合法”错误地解释成“实现失败”。

本次只修改 Agent 控制循环，不更改题单、模型、官方适配器默认值、评分器或历史实验。修改后的效果需要新的、预注册的完整十题单次评测确认。

## 已发生的错误

### 1. 工具协议与状态错误

- `scratch/solve.py` 尚不存在时，模型调用 `replace_function`、`read_file` 或 `run_python`。这些动作没有可能成功，却被工作流计入 repair。
- 必须使用高层金融算子的任务中，模型在第一份适配器被 AST 门拒绝后，尝试修改或读取一个并未写入的 `solve.py`。
- 输入 CSV/JSON 被复制到 scratch。运行时本来已提供只读输入路径和数据画像；这些复制既不改变实现，也不增加证据，却曾被当作 mutation，清空停滞计数。
- 真正执行失败后，模型有时重新 `list_files`、复制输入或浏览无关文件，丢弃了已有 traceback、源码片段和失败阶段证据。
- 局部编辑、自动执行和父动作共用一个结果状态。源码写入成功但自动执行失败时，轨迹中的父编辑也显示为失败；若不区分“代码已改变”和“程序执行失败”，模型容易重复旧补丁。

直接轨迹证据：

- v6.6 十题共记录 116 个 tool event，其中 93 个为失败状态；包括 46 个 `replace_text` 失败记录以及 37 个 `run_python` 中的 33 个失败。这里包含控制器自动运行及其父编辑的关联记录，因此是循环负担，不等同于 93 个独立根因。
- v6.7 中三个已验证算子任务在最终通过前共消耗 17 次模型响应。几何跳扩散的序列是“无效适配器 → 修改不存在文件 → 读取不存在文件 → 正确适配器”；隐含波动率也是同一模式。Fama-French 在正确适配器前还执行了两次输入复制、两次目录列举和一次读取不存在文件。
- v6.7 六个已提交结果和 DCC 部分轨迹共记录 57 个 tool event，其中 22 个失败。说明算子改善了计算正确性，但没有消除控制循环浪费。

### 2. 实现错误

- 语法和未定义符号：几何跳扩散、Fama-French、美国期权均出现。
- 路径和输入类型：方差互换把 JSON 当作 DataFrame，并使用错误的相对路径。
- 日期/索引对齐：Fama-French 曾按数组长度截断，而不是按日期键取交集。
- 输出契约：DCC 和 local-vol 出现缺文件或不完整产物。
- 完成协议：v6.6 亚洲期权 checker 25/25，但 Agent 仍以 incomplete 退出，严格 pass@1 计 0。

### 3. 方法与数值错误

- 美国期权同时存在 CN/PSOR、股息边界条件等方法问题，不能只修未定义变量。
- 隐含波动率既有 Newton 收敛/覆盖率问题，也有误差汇总实现错误。
- local-vol 是计算方法、输出协议和循环停滞混合失败，不能从“程序跑完”推断数值正确。

### 4. 模型服务与评测基础设施错误

- v6.6 有 79 次模型请求、78 次完整响应；一次服务请求未完成，不能算作生成失败或算法失败。
- v6.7 因 scratch 数据别名可写，DCC 代码覆盖冻结输入，runner 正确终止批次。
- v6.7.1 因只读 checker 的 staging 副本无法重写路径，首题 Agent 完成后 runner 中断。
- 上述两次中断均已保留，不能与后续结果拼接，也不能当作模型 pass@1。

## 按 Agent 设计原则完成的循环修改

### 状态感知的工具许可

控制器现在根据 `solver_exists`、`required_operator` 和最近一次真实执行状态决定工具是否有意义。

- 必用高层算子且尚无 solver 时，只允许 `write_file` 创建 `scratch/solve.py`。
- 普通任务尚无 solver 时，读取、局部修改或运行 `scratch/solve.py` 会被识别为 build 协议错误，并明确要求完整写入。
- 适配器真实执行失败后，目录列举、搜索、复制输入和读取无关文件会被拒绝；允许读取当前 solver 或进行有证据的局部修改。

这体现“先缩小动作空间，再让模型决策”，而不是仅靠更长提示词劝模型不要走错路。

### 将协议错误与实现/方法失败分开

新的策略观察包含：

- `controller_policy`
- `policy_phase`
- `allowed_next_tools`
- `required_next_step`

被控制器拒绝的动作没有运行代码，不再增加 `failed_runs`、`repair_attempts`，也不再写入虚假的 failure kind。真正带 `returncode` 的执行失败仍进入原有分类：路径、类型、对齐、数值、超时等；结构化三层验证仍可把反馈路由到 implementation 或 method review。

### 重新定义“进展”

- 非代码检查文件的写入或复制不再清空停滞状态。
- `copy_file` 现在只允许从可见输入复制 Python 模板到 scratch 的 Python 文件。
- CSV、JSON 等数据必须留在只读 input，通过 `TASK_DIR` 加载；`fetch_data.py` 仍由专门规则拒绝作为 solver。
- 成功的 solver 源码变更、真实执行和验证仍是有效进展。

### 保留验证优先的闭环

本次没有取消既有的三层验证和失败分流：

1. 结构检查：文件、字段、类型、形状和输出契约。
2. 计算检查：有限值、索引一致、数值条件与收敛。
3. 独立交叉检查：回归重构、定价边界/网格、风险尾部重算等。

循环变化只保证每个工具动作与当前状态匹配；它不把结构检查冒充数值正确，也不把公开 checker 通过冒充隐藏集泛化。

## 预期影响与验证边界

这次修改应减少两类浪费：solver 创建前的无效读/改/跑，以及执行失败后的重新探索。它不能单独解决尚无高层算子的 DCC、local-vol 等方法问题，也不能凭单元测试证明 pass@1 上升。

代码测试覆盖：

- 必用算子时只允许首次完整写入；
- 不存在 solver 的编辑被归类为 build 协议；
- 执行失败后的探索重置被拦截；
- 控制器策略拒绝不污染失败计数；
- 数据复制不再伪装成实现进展；
- Python 模板复制仍保持兼容。

下一步应在代码提交后，按 `scripts/dev_local.py`、固定模型/题单/预算、全新实验名运行一次完整十题。只有 10 个唯一结果全部核验后，才能报告新的严格 pass@1。
